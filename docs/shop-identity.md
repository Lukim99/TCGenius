# 상점 상품 ID와 구매 제한

상점 상품의 `shopId`는 위치·상점 이름·판매 아이템 번호와 독립적인 식별자다. 상품을 이동하거나 순서를 바꿀 때 그대로 유지한다. 같은 아이템을 별도 상품으로 추가할 때는 새 ID를 발급한다.

- 기존 상품: 조회 응답에 `legacy.<최초 상점 이름의 base64url>.<최초 인덱스>` 형식의 ID를 제공한다. 이 ID는 기존 `shopPurchases[상점][인덱스]`와 `ShopState[상점][인덱스]`를 계속 참조한다. 이동 이후에도 **ID에 담긴 최초 주소**를 사용하며 현재 인덱스를 사용하지 않는다.
- 신규 상품: `shop_<32자리 랜덤 16진수>` ID를 발급하고 개인·전체 기록의 `@items[shopId]`에 저장한다.
- 조회와 서버 시작에서는 Shop, ShopState, 유저 데이터를 일괄 변경하지 않는다. 관리자가 Shop 저장을 명시적으로 실행하면 ID가 상품 설정에 함께 저장된다. 상품 내용·가격·수량·기존 제한 기록은 초기화하지 않는다.

관리자 상품 편집과 패키지 생성은 ID를 자동 처리한다. RAW JSON 편집이나 별도 스크립트에서도 기존 `shopId`를 보존해야 한다. 신규 ID는 `require('./shop_catalog').newShopItemId()`로 생성할 수 있다. ID 누락·중복과 잘못된 기존 ID는 저장을 거부한다. GET `/api/data/Shop`의 `revision`을 PUT 요청에 함께 보내야 하며, 다른 편집이 먼저 저장됐으면 409로 거부한다.

패키지 등록은 Bundle·Item·Shop을 한 트랜잭션으로 저장한다. 동시 편집이 감지되면 셋 모두 저장하지 않아, 상점 등록 없이 구성품만 남는 상태를 방지한다.

웹 구매와 상품별 제한 초기화는 `index` 대신 `shopId`를 전송한다. 배포 전에 열어둔 구버전 화면에서는 새로고침이 필요하다. 채팅의 상품 번호 명령은 현재 목록에서 상품을 선택하되 기록은 고정 ID로 관리한다. 다른 상점으로 옮긴 상품의 제한 초기화는 현재 소속 상점을 기준으로 해당 상품의 기록만 초기화한다.

이미 과거의 인덱스 변경으로 잘못 연결된 기록은 상품 변경 이력 없이 원래 대상을 판별할 수 없다. 현재 저장된 연결을 보존하며 추측해서 재배정하지 않는다. 구버전 서버는 ID를 인식하지 못하므로 신·구 버전 서버를 동시에 운영하지 않는다.

검증: `node tests/shop_identity.test.js` — DynamoDB를 메모리로 대체하여 삭제, 이동, 동일 아이템 추가, 구매, 초기화, 기간 만료, 동시 편집을 확인한다.
